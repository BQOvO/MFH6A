## What it is

MFH6A is a MaaFramework project: MaaFramework recognizes the game window and drives it through pipelines, while MXU provides the GUI.

It does not read process memory, does not touch save files, and does not inject into the game. Everything it does is "look at the screen, press a button" — the same way a person at the keyboard would. That is how MaaFramework-based tools work in general: recognition via templates and OCR, execution via simulated input.

> It is still a skeleton. `Tutorial` is a sample task used to verify the pipeline runs end to end. Real gameplay flows have not been written yet.

## Usage

### Run it

An unpacked release looks like this:

```
MFH6A/
├── mxu.exe          MXU GUI
├── maafw/           MaaFramework runtime (DLLs)
├── interface.json   Project descriptor read by MXU
└── resource/        Resource pack (pipelines, images, OCR models)
```

Double-click `mxu.exe`, choose the game window under "Select window" on the right, tick the tasks, then hit "Start".

**The working directory must be the unpacked root.** MXU resolves `interface.json` and `maafw/` relative to itself; launching it from elsewhere gives you a blank window or a failed connection.

### Requirements

- Windows 10/11 x64
- Do not minimize the game window — MaaFramework captures window pixels, and a minimized window has none
- Some actions need the window in the foreground; background clicks do not work on exclusive fullscreen. "Windowed" or "Borderless" is more reliable

## FAQ

**No window to select?**
Make sure the game is running and not minimized, then hit the refresh button next to "Select window". MXU lists the titles of all currently visible windows.

**Nothing happens after Start?**
Read the log panel on the right. When a pipeline cannot find what it looks for, it retries and logs `recognition failed` — that tells you which step it is stuck on.

**Recognition is off?**
Template matching is sensitive to resolution and DPI scaling. Set Windows display scaling to 100%, or re-capture the template images.

**Can it run unattended?**
Yes, as long as the window stays unminimized. True background operation (locked screen, another user session) fails because there are no pixels to capture.

## Development

Generated with [create-maa-project](https://github.com/Windsland52/create-maa-project) 3.8.0, using the **agent** template (Python custom logic) and the **MXU** runtime.

### Layout

```
MFH6A/
├── agent/                  Python agent
│   ├── main.py             Entry point (checks the Python version)
│   ├── agent_runtime.py    Loads and registers everything under custom/
│   ├── custom/action/      Custom actions
│   ├── custom/reco/        Custom recognitions
│   ├── custom/sink/        Custom sinks
│   └── utils/              PI env vars, argument parsing, logging, paths
├── resource/base/
│   ├── pipeline/           Pipeline definitions (JSON)
│   ├── image/              Template images
│   └── model/ocr/          OCR models
├── tasks/                  Task definitions referenced by interface.json
├── interface.json          PI v2 project descriptor
├── maa-project.json        create-maa-project configuration
├── tools/schema/           JSON Schemas for editor completion and validation
└── runtimes/, plugins/, libs/   Runtime assets, generated by --update, never committed
```

### Setup

```bash
uv sync                                   # Python deps
pnpm install                              # dev tooling (formatting, schema validation)
create-maa-project --update ocr-models    # OCR models (not tracked)
create-maa-project --update maafw         # MaaFramework runtime (not tracked)
```

Opening the project in VS Code runs `uv sync` and `pnpm install --frozen-lockfile` once via `.vscode/tasks.json`.

### Debugging

```bash
uv run python agent/main.py   # starts as an AgentServer for MXU or the MaaSupport extension
```

In VS Code use the `Maa Agent: Debug` configuration from `.vscode/launch.json`; the mapping lives in `maatools.config.mts`.

Pipeline changes do not require restarting MXU — just re-run the task. Python changes do.

### Adding Python dependencies

```bash
uv add <package>
create-maa-project --update python-deps
```

`uv add` only touches `pyproject.toml`, `uv.lock` and the local `.venv`. `requirements.in` / `requirements.txt` are regenerated from `pyproject.toml` by `--update python-deps`. Release builds install from `requirements.txt`, so this step is mandatory — commit all four files together, or the release will be missing the dependency that works locally.

### Releasing

CI is not enabled yet. To turn it on:

```bash
create-maa-project --add github
```

Pushing a tag such as `v0.1.0` then triggers `.github/workflows/release.yml`, where CI re-downloads MaaFramework, MXU and the OCR models before packaging.

The tag is the version: packaging writes it back into the packaged `interface.json` `version` field, while the repository copy keeps the internal development version `v0.0.0-dev` and never has to be edited for a release.
